# Checked responder replies

The same-Host public delivery Service retains `contractVersion: 1` and adds optional `replyContextVersion: 1`, `replyReceiptVersion: 1` and `replyFenceVersion: 1`. Qualified Feishu/Lark accounts advertise `reply-context-checked`, `reply-receipt-checked` and `reply-fence-checked` beside the existing external-consumer capabilities.

`qualifyReplyChecked(botId, route, {expectedFingerprint, signal})` reads the exact source using that account. It verifies original `messageId`, `conversationId`, `threadId`, `rootId` and `parentId`, returning a route with the sender Open ID resolved by the responding application. The caller's ingress `actorId` is not assumed portable between Lark apps. Qualification never sends, scans history or grants a group. Missing/deleted sources refuse with `source-not-found`; permission refusals use `reply-permission-denied`; transport or unclassified reads remain `source-unavailable`. Changed routes use `stale-route`. Registration removal, account replacement or cancellation fence the result.

`replyChecked(botId, qualifiedRoute, text, {expectedFingerprint, signal, receipt: true, beforeSend})` checks the exact source again under the responding account. An optional synchronous `beforeSend(): boolean` runs after remote validation and immediately before the SDK send; anything other than `true` refuses with `stale-route`. This is a trusted same-Host consumer callback, not an RPC payload or an authentication bypass. The callback must not perform asynchronous work. Provider cancellation and account/client identity are still checked.

An opted-in reply returns `{sent: true, receipt: {version: 1, messageId, conversationId}}`; missing or mismatched returned IDs after dispatch are `reply-result-unknown`. Legacy calls without `receipt` retain `{sent: true, messageId}`. A receipt identifies provider acceptance, not Human delivery or read status. A thread reply cannot fall back to a group mainline. Consumers own durable intents, per-account provenance, authorization and safe unknown-outcome behavior; this contract does not start a native provider Session or create a second transcript.

These optional features require per-account qualification and real application/group testing before consumer production use. A passing fixture test is not proof that a second application has permission to read or reply in a real group.
