# Checked responder replies

The same-Host public delivery Service retains `contractVersion: 1` and adds optional `replyContextVersion: 1`, `replyReceiptVersion: 1` and `replyFenceVersion: 1`. Qualified Feishu/Lark accounts advertise `reply-context-checked`, `reply-receipt-checked` and `reply-fence-checked` beside the existing external-consumer capabilities.

`qualifyReplyChecked(botId, route, {expectedFingerprint, signal})` reads the exact source using that account. It verifies original `messageId`, `conversationId`, `threadId`, `rootId` and `parentId`, returning a route with the sender Open ID resolved by the responding application. The caller's ingress `actorId` is not assumed portable between Lark apps. Qualification never sends, scans history or grants a group. Missing/deleted sources refuse with `source-not-found`; permission refusals use `reply-permission-denied`; transport or unclassified reads remain `source-unavailable`. Changed routes use `stale-route`. Registration removal, account replacement or cancellation fence the result.

`replyChecked(botId, qualifiedRoute, text, {expectedFingerprint, signal, receipt: true, beforeSend})` checks the exact source again under the responding account. An optional synchronous `beforeSend(): boolean` runs after remote validation and immediately before the SDK send; anything other than `true` refuses with `stale-route`. This is a trusted same-Host consumer callback, not an RPC payload or an authentication bypass. The callback must not perform asynchronous work. Provider cancellation and account/client identity are still checked.

An opted-in reply returns `{sent: true, receipt: {version: 1, messageId, conversationId}}`; missing or mismatched returned IDs after dispatch are `reply-result-unknown`. Legacy calls without `receipt` retain `{sent: true, messageId}`. A receipt identifies provider acceptance, not Human delivery or read status. A thread reply cannot fall back to a group mainline. Consumers own durable intents, per-account provenance, authorization and safe unknown-outcome behavior; this contract does not start a native provider Session or create a second transcript.

These optional features require per-account qualification and real application/group testing before consumer production use. A passing fixture test is not proof that a second application has permission to read or reply in a real group.

## QQ group text consumer

Qualified QQ applications advertise `exclusive-text-consumer`, `reply-text-checked`, `reply-context-checked`, `reply-receipt-checked`, and `reply-fence-checked`. Their fingerprint combines configured AppID with the authenticated native `/users/@me` Bot identity. Credentials and the SDK remain owned by the Provider.

`consumeInbound` persists `external-consumer` mode and takes one exclusive same-Host lease. It accepts text-only `GROUP_AT_MESSAGE_CREATE` events, using application-scoped group/member OpenIDs and the native message ID. It awaits canonical consumer admission; private messages, ordinary group traffic, attachments and compound/quoted payloads are excluded. No standalone Harness conversation runs while this mode is active. Disposing the lease, reconnecting, restarting or replacing credentials does not restore the standalone consumer; a fresh lease is required.

QQ qualification uses bounded process-local proof of the exact event delivered to this application. It cannot read another application's source, fetch group history, or resume a durable platform cursor. The event reports `provider-redelivery`, `resumeCursor: false`, and `gapPossible: true`; the consumer owns canonical deduplication. Source proof expires after five minutes or five attempted replies. Qualification checks the exact message, group and actor, and refuses thread routes.

Checked replies use the original group's native `msg_id` and return the native response `id` only after a valid send response. `reply-window-expired`, `reply-limit-exceeded` and `reply-rate-limited` preserve definite platform refusals; membership/permission refusals use `reply-permission-denied`. An interrupted send or unclassified server failure remains `reply-result-unknown`, with no proactive fallback or automatic resend. This account does not yet advertise checked proactive messaging, media or group history.

These limits follow the current [official group send contract](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html) and [group mention event](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_at_message_create.html). The [ordinary group event](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html) requires receiving all messages and is outside this text consumer's initial scope.
